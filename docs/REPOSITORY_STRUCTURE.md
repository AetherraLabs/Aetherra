# Repository Structure

This is the source-of-truth policy for what belongs in Aetherra source control.
The repository should contain the source, documentation, tests, configuration,
and reproducible inputs needed to build and operate Aetherra. Generated output
belongs in local working directories, CI artifacts, or release assets instead of
Git history.

## Belongs In Source Control

- Source code for Aetherra systems, services, plugins, interfaces, and tools.
- Hand-written documentation, system specifications, policies, and operator
  guides under `docs/`.
- Tests, fixtures, and small deterministic examples required to verify behavior.
- Dependency manifests and lockfiles used to reproduce development, CI, and
  release environments.
- CI workflows, security policies, packaging recipes, and small configuration
  files required by the project.

## Must Be Regenerated Or Published Elsewhere

- Build outputs such as `build/`, `dist/`, `dist-packages/`, wheels, installers,
  packaged application folders, and release bundles.
- Runtime state such as databases, logs, audit streams, outbox files, temporary
  state, local memory stores, and machine-specific configuration.
- Cache folders such as `__pycache__/`, `.pytest_cache/`, `.ruff_cache/`,
  `.mypy_cache/`, `.cache/`, model caches, and downloaded dependency caches.
- Generated reports such as coverage output, security scanner output, quality
  gate artifacts, local validation reports, and generated file indexes unless a
  specific report is intentionally promoted into `docs/`.
- Vendored dependency trees such as `node_modules/`, `site-packages/`, copied
  Python environments, frontend dependency installs, and packaged third-party
  runtime bundles.

## Review Rule

Before committing a large file or directory, ask whether it is an input or an
output. Inputs belong in source control when they are necessary, reviewable, and
stable. Outputs should be regenerated by tools, uploaded as CI artifacts, or
attached to releases.

If a generated file needs to become a durable project record, move it into an
appropriate `docs/` or `docs/reports/` location and make the purpose explicit in
the commit message.
